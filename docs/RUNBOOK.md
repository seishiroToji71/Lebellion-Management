# RUNBOOK — операционные аварийные процедуры

> Только для эксплуатации. Обычные пользователи и обычная поддержка сюда не заходят.

## 1. Аварийное восстановление доступа FOUNDER (admin CLI)

### Когда применяется

Единственный случай: FOUNDER потерял доступ **и к email, и к телефону**, поэтому
self-service сброс (`POST /auth/password-reset/*`) для него недоступен. Для FOUNDER
recovery-инвайта не существует (recovery-инвайт — только для EMPLOYEE и для сброса
пароля BRANCH_MANAGER Фаундером). Это последний резерв.

### Статус реализации

**Не реализовано в коде (v1).** Здесь зафиксирована спецификация; сама CLI-команда
пишется отдельной задачей. Пока восстановление выполняется вручную по этому разделу
доверенным оператором с доступом к VPS.

### Предусловия (все обязательны)

- Физический/SSH-доступ к VPS в Узбекистане, где живёт БД.
- Подтверждённая заявка от владельца бизнеса вне канала приложения (например, звонок +
  письменное подтверждение). Оператор фиксирует, кто и когда запросил сброс.
- Известны `organization_id` и идентификатор целевого FOUNDER.

### Что делает процедура

1. Генерирует **временный** пароль, сохраняет `app_user.password_hash`
   (`DelegatingPasswordEncoder`) и ставит `must_change_password = true` —
   FOUNDER обязан сменить пароль при первом входе.
2. Отзывает все сессии: `token_version = token_version + 1` и помечает все строки
   `refresh_token` пользователя как `revoked_at = now()`,
   `revoked_reason = 'ADMIN_CLI_RESET'`.
3. Пишет в `AuditLog` запись типа **`PASSWORD_RESET_BY_ADMIN_CLI`**: кто (оператор),
   когда, целевой `user_id`, `organization_id`, основание заявки. Запись append-only.
4. Временный пароль передаётся владельцу по защищённому вне-приложенческому каналу и
   немедленно инвалидируется сменой при первом входе.

### Планируемый интерфейс команды (черновик, ещё не в коде)

```
lebellion-admin reset-founder \
  --org <organization_id> \
  --user <user_id | email | phone> \
  --requested-by "<кто запросил, для аудита>"
```

Команда должна:
- работать только для роли `FOUNDER`;
- отказываться, если у пользователя есть рабочий email/телефон (тогда — self-service);
- никогда не печатать пароль в лог/историю shell (только на stdout один раз);
- быть идемпотентной по аудиту (каждый запуск — новая AuditLog-запись).

### Что запрещено

- Не восстанавливать доступ по устной просьбе без письменного подтверждения.
- Не выполнять прямые `UPDATE` по БД в обход процедуры (нет AuditLog → потеря следа).
- Не переиспользовать этот путь для BRANCH_MANAGER — для менеджера сброс делает FOUNDER
  через recovery-инвайт из приложения.
